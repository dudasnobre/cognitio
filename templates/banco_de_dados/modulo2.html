2. Modelo Relacional — Tabelas, Linhas e Colunas

O modelo relacional organiza os dados em tabelas. Cada tabela tem colunas (características) e linhas (registros). É o modelo mais usado no mundo há mais de 50 anos.

- Anatomia de uma Tabela

Imagine uma tabela de clientes: cada coluna é um tipo de dado (nome, cidade, saldo) e cada linha é um cliente real. A interseção de linha e coluna é uma célula.

  • Tabela — conjunto de dados sobre um mesmo assunto (ex: clientes)
  • Coluna — característica dos dados (ex: nome, email, cidade)
  • Linha — um registro individual (ex: dados de Ana Silva)
  • Chave Primária (PK) — identifica cada linha de forma única; nunca nula ou duplicada

- Chave Estrangeira: Relacionando Tabelas

Uma Chave Estrangeira (FK) é uma coluna que referencia a chave primária de outra tabela. Com ela, a tabela pedidos guarda apenas o cliente_id em vez de repetir todos os dados do cliente.

- Tipos de Dados Comuns no SQL

  • INTEGER — números inteiros: 1, 42, -5
  • REAL / DECIMAL — números decimais: 3.14, 1500.50
  • TEXT / VARCHAR(n) — texto: "Ana Silva", "São Paulo"
  • DATE / DATETIME — datas e horários: "2025-01-15"

- Criando sua Primeira Tabela

CREATE TABLE alunos (
    id      INTEGER PRIMARY KEY AUTOINCREMENT,
    nome    TEXT    NOT NULL,
    email   TEXT    UNIQUE,
    nota    REAL    DEFAULT 0
);
PRAGMA table_info
No SQLite, você pode ver a estrutura de qualquer tabela com: PRAGMA table_info(nome_da_tabela);

- Restrições (Constraints)

Além do tipo de dado, cada coluna pode ter regras que garantem a integridade da informação:

  • PRIMARY KEY — identifica a linha de forma única (não pode repetir nem ser nula)
  • NOT NULL — a coluna é obrigatória, não pode ficar vazia
  • UNIQUE — não permite valores repetidos (ex: e-mail)
  • DEFAULT — valor usado automaticamente quando nada é informado
  • FOREIGN KEY — garante que o valor exista de fato na tabela referenciada

- Normalização (Por que Separar em Várias Tabelas?)

Um erro comum de iniciante é guardar tudo numa tabela só — por exemplo, repetir o nome e o e-mail do cliente em toda linha de pedido. Isso causa dados duplicados e inconsistentes (e se o cliente mudar de e-mail, você teria que atualizar centenas de linhas). A solução é a normalização: separar os dados em tabelas menores e relacioná-las por chave estrangeira.

Dados duplicados = dados inconsistentes
Se o nome de um cliente aparece em 50 linhas de pedidos e você atualiza só uma, agora você tem 49 registros com informação desatualizada. Guardar o dado uma única vez (na tabela clientes) e referenciá-lo por cliente_id evita esse problema.
Exercício rápido
No terminal abaixo, use o snippet "Criar tabela" para criar a tabela alunos, depois rode PRAGMA table_info(alunos); para conferir a estrutura criada.

- Resumo do Módulo

  • Tabelas guardam dados em linhas (registros) e colunas (características)
  • Chave Primária (PK) identifica cada linha; Chave Estrangeira (FK) relaciona tabelas
  • Constraints (NOT NULL, UNIQUE, DEFAULT) garantem integridade dos dados
  • Normalização evita duplicação de dados espalhando-os em tabelas relacionadas
